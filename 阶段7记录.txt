阶段 7：禁用密码登录验证记录

一、阶段目标

本阶段目标是在 VM2 SSH 目标机上禁用 SSH 密码登录，验证弱口令暴力破解在关闭密码认证后失效，同时保证合法管理端 VM1 仍然可以通过 SSH 私钥登录 VM2。

本阶段的核心原则是：

必须先确认私钥登录成功，再禁用密码登录。

如果未配置好公钥认证就直接关闭 PasswordAuthentication，可能导致无法再通过 SSH 远程登录 VM2。因此，本阶段先在 VM1 上生成密钥对并将公钥添加到 VM2，然后验证私钥登录成功，最后再关闭密码认证。

本阶段完成后应证明：

1. VM1 已生成 SSH 密钥对。
2. VM1 的公钥已添加到 VM2 的 testuser 的 authorized_keys 中。
3. VM1 可以使用私钥登录 VM2。
4. VM2 已关闭 PasswordAuthentication。
5. sshd -T 显示 passwordauthentication no。
6. VM3 使用密码方式登录 VM2 失败。
7. VM1 使用私钥仍然可以登录 VM2。
8. VM1 平台改用私钥路径后仍可连接 VM2。
9. VM1 平台安全检查可以显示 passwordauthentication no。

二、实验环境

本阶段继续使用前面阶段的三台虚拟机。

1. VM1：SSH-VM1
   - 角色：管理端
   - 系统：Ubuntu Desktop
   - Host-only IP：192.168.45.101
   - 用途：生成 SSH 密钥对，使用私钥登录 VM2，并运行 Flask SSH 管理平台

2. VM2：SSH-VM2
   - 角色：SSH 目标机 / 被管理端
   - 系统：Ubuntu Server
   - Host-only IP：192.168.45.102
   - 用途：运行 OpenSSH Server，关闭密码登录，保留公钥认证

3. VM3：SSH-VM3
   - 角色：攻击端
   - 系统：Kali Linux
   - Host-only IP：192.168.45.103
   - 用途：验证禁用密码登录后，攻击端无法再使用 testuser / 123456 通过密码认证登录 VM2

实验账号：

用户名：testuser
原密码：123456

说明：阶段 7 完成后，testuser 的系统密码仍然存在，但 SSH 服务不再接受密码认证，因此该密码不能再用于 SSH 远程登录。

三、阶段 7 操作流程

本阶段按以下顺序执行：

1. VM1 生成 SSH 密钥对。
2. VM1 将公钥复制到 VM2。
3. VM1 验证私钥登录 VM2 成功。
4. VM2 修改 SSH 配置，关闭密码认证。
5. VM2 使用 sshd -t 检查语法。
6. VM2 重启 SSH 服务。
7. VM2 使用 sshd -T 查看最终生效配置。
8. VM3 验证密码登录失败。
9. VM1 验证私钥登录仍然成功。
10. VM1 平台改用私钥连接 VM2。
11. VM1 平台安全检查显示 passwordauthentication no。
12. 记录阶段中遇到的配置冲突问题和解决过程。

四、VM1 生成 SSH 密钥对

1. 创建 .ssh 目录

在 VM1 上执行：

cd ~
mkdir -p ~/.ssh
chmod 700 ~/.ssh

2. 生成 Ed25519 密钥对

在 VM1 上执行：

ssh-keygen -t ed25519 -f ~/.ssh/vm2_test_key

系统提示输入 passphrase 时，直接按 Enter，不设置 passphrase。

不设置 passphrase 的原因：

1. 本实验属于本地隔离环境中的验证实验。
2. 阶段 4 的 Flask 平台代码当前只支持直接读取私钥文件，没有额外处理私钥 passphrase。
3. 为保证阶段 7 平台私钥连接验证顺利，使用无 passphrase 的实验密钥。

3. 检查密钥文件

执行：

ls -l ~/.ssh/vm2_test_key*

预期生成两个文件：

~/.ssh/vm2_test_key
~/.ssh/vm2_test_key.pub

其中：

vm2_test_key 是私钥文件，只保存在 VM1。
vm2_test_key.pub 是公钥文件，需要添加到 VM2。

4. 设置密钥权限

执行：

chmod 600 ~/.ssh/vm2_test_key
chmod 644 ~/.ssh/vm2_test_key.pub

5. 查看公钥指纹

执行：

ssh-keygen -lf ~/.ssh/vm2_test_key.pub

记录该指纹，用于后续和 VM2 authorized_keys 中的公钥进行比对。

五、VM1 将公钥复制到 VM2

在关闭密码登录前，VM2 仍然允许密码认证，因此可以使用 ssh-copy-id 将 VM1 的公钥复制到 VM2。

在 VM1 上执行：

ssh-copy-id -i ~/.ssh/vm2_test_key.pub testuser@192.168.45.102

输入 testuser 当前密码：

123456

成功后系统提示类似：

Number of key(s) added: 1
Now try logging into the machine...

该步骤说明 VM1 的公钥已被添加到 VM2 上 testuser 用户的 ~/.ssh/authorized_keys 文件中。

六、VM1 验证私钥登录成功

在 VM1 上执行：

ssh -i ~/.ssh/vm2_test_key -o IdentitiesOnly=yes testuser@192.168.45.102

登录成功后在 VM2 会话中执行：

whoami
hostname
exit

预期输出：

whoami 显示 testuser。
hostname 显示 VM2 的主机名，例如 ubuntu-server。

该步骤是关闭密码登录前的关键验证，说明公钥认证已经可用。只有确认私钥登录成功后，才可以继续关闭 PasswordAuthentication。

七、VM2 确认 authorized_keys 中已有 VM1 公钥

在 VM2 上以 testuser 身份执行：

ls -l ~/.ssh
cat ~/.ssh/authorized_keys

也可以查看 authorized_keys 中的公钥指纹：

ssh-keygen -lf ~/.ssh/authorized_keys

将该指纹与 VM1 上 vm2_test_key.pub 的指纹进行比对，确认 VM2 中保存的是 VM1 生成的公钥。

八、VM2 初次修改 PasswordAuthentication

阶段 2 中已创建 SSH 配置片段：

/etc/ssh/sshd_config.d/99-lab-basic.conf

因此，阶段 7 一开始尝试修改该文件。

在 VM2 上执行：

sudo nano /etc/ssh/sshd_config.d/99-lab-basic.conf

将：

PasswordAuthentication yes

修改为：

PasswordAuthentication no

修改后文件内容为：

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
MaxAuthTries 6
LogLevel VERBOSE

查看配置文件：

sudo cat /etc/ssh/sshd_config.d/99-lab-basic.conf

确认该文件中已经显示：

PasswordAuthentication no

九、检查最终配置时发现问题

修改 /etc/ssh/sshd_config.d/99-lab-basic.conf 后，执行：

sudo sshd -T | grep -E '^(passwordauthentication|pubkeyauthentication|permitrootlogin|permitemptypasswords|maxauthtries|loglevel)'

实际结果中仍然显示：

passwordauthentication yes

同时，VM3 上执行以下命令：

ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no testuser@192.168.45.102

输入密码 123456 后仍然能够成功登录 VM2。

这说明：

1. 99-lab-basic.conf 中虽然写了 PasswordAuthentication no。
2. 但 OpenSSH 最终生效配置仍然是 passwordauthentication yes。
3. 阶段 7 的禁用密码登录尚未成功。
4. 阶段 7 必须以 sshd -T 的输出作为最终判断依据，而不能只看配置文件内容。

十、排查配置冲突

为查找导致 passwordauthentication yes 的配置来源，在 VM2 上执行：

sudo grep -RniE '^\s*(PasswordAuthentication|KbdInteractiveAuthentication|ChallengeResponseAuthentication)' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/*.conf

实际输出显示：

/etc/ssh/sshd_config:71:KbdInteractiveAuthentication no
/etc/ssh/sshd_config.d/50-cloud-init.conf:1:PasswordAuthentication yes
/etc/ssh/sshd_config.d/99-lab-basic.conf:2:PasswordAuthentication no

该结果说明系统中存在配置冲突：

1. /etc/ssh/sshd_config.d/50-cloud-init.conf 中写有 PasswordAuthentication yes。
2. /etc/ssh/sshd_config.d/99-lab-basic.conf 中写有 PasswordAuthentication no。
3. 最终 sshd -T 显示 passwordauthentication yes。
4. 导致 VM3 仍然可以通过密码登录。

问题原因：

Ubuntu Server 的 cloud-init 可能会生成 /etc/ssh/sshd_config.d/50-cloud-init.conf，其中包含 PasswordAuthentication yes。该配置影响 OpenSSH 的最终生效结果，导致仅修改 99-lab-basic.conf 不足以关闭密码认证。

十一、修复 50-cloud-init.conf 配置

为解决上述配置冲突，在 VM2 上修改：

/etc/ssh/sshd_config.d/50-cloud-init.conf

执行：

sudo nano /etc/ssh/sshd_config.d/50-cloud-init.conf

将其中的：

PasswordAuthentication yes

修改为：

PasswordAuthentication no

保存退出后查看确认：

sudo cat /etc/ssh/sshd_config.d/50-cloud-init.conf

预期结果：

PasswordAuthentication no

十二、检查 SSH 配置语法

在 VM2 上执行：

sudo sshd -t && echo "sshd config syntax OK"

如果输出：

sshd config syntax OK

说明 SSH 配置语法正确，可以继续重启 SSH 服务。

十三、重启 SSH 服务

在 VM2 上执行：

sudo systemctl restart ssh
sudo systemctl status ssh --no-pager

预期结果：

Active: active (running)

说明修改配置后 SSH 服务仍然正常运行。

十四、验证最终生效配置

在 VM2 上执行：

sudo sshd -T | grep -E '^(passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication|permitrootlogin|permitemptypasswords|maxauthtries|loglevel)'

预期结果应包含：

passwordauthentication no
kbdinteractiveauthentication no
pubkeyauthentication yes
permitrootlogin no
permitemptypasswords no
maxauthtries 6
loglevel VERBOSE

关键检查项：

1. passwordauthentication no
   - 说明密码认证已关闭。

2. kbdinteractiveauthentication no
   - 说明键盘交互式认证关闭，避免通过 PAM 交互方式继续接受密码。

3. pubkeyauthentication yes
   - 说明公钥认证仍然开启，VM1 可以继续用私钥登录。

阶段 7 的配置是否成功，应以 sshd -T 输出为准。

十五、VM3 验证密码登录失败

在 VM3 上执行：

ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -o KbdInteractiveAuthentication=no testuser@192.168.45.102

或者：

二十一、阶段 7 遇到的问题与解决

问题描述：

修改 /etc/ssh/sshd_config.d/99-lab-basic.conf 中 PasswordAuthentication no 后，执行 sshd -T 仍显示：

passwordauthentication yes

同时 VM3 仍然可以使用：

ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no testuser@192.168.45.102

通过密码 123456 登录 VM2。

原因分析：

通过 grep 检查发现：

/etc/ssh/sshd_config.d/50-cloud-init.conf:1:PasswordAuthentication yes
/etc/ssh/sshd_config.d/99-lab-basic.conf:2:PasswordAuthentication no

系统中存在 cloud-init 生成的 50-cloud-init.conf，其中仍然设置 PasswordAuthentication yes，导致 OpenSSH 最终生效配置没有变为 no。

解决方法：

将 /etc/ssh/sshd_config.d/50-cloud-init.conf 中的：

PasswordAuthentication yes

修改为：

PasswordAuthentication no

然后执行：

sudo sshd -t
sudo systemctl restart ssh
sudo sshd -T | grep -E '^(passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication|permitrootlogin|permitemptypasswords|maxauthtries|loglevel)'

确认最终生效结果为：

passwordauthentication no
kbdinteractiveauthentication no
pubkeyauthentication yes

最终验证：

1. VM3 密码登录失败。
2. VM1 私钥登录成功。
3. VM1 平台私钥连接成功。
4. 平台安全检查显示 passwordauthentication no。

经验总结：

SSH 配置修改后不能只看配置文件内容，必须使用 sshd -T 查看最终生效配置。尤其在 Ubuntu Server 中，/etc/ssh/sshd_config.d/ 目录下可能存在 cloud-init 生成的配置文件，导致多个配置片段之间产生冲突。

二十四、阶段 7 实验结论

本阶段验证了禁用 SSH 密码登录对弱口令暴力破解攻击的防御效果。

首先，在 VM1 管理端生成 Ed25519 密钥对，并将公钥添加到 VM2 的 testuser authorized_keys 中。确认 VM1 可以使用私钥成功登录 VM2 后，再开始关闭 SSH 密码认证。初次修改 /etc/ssh/sshd_config.d/99-lab-basic.conf 中的 PasswordAuthentication no 后，发现 sshd -T 仍显示 passwordauthentication yes，且 VM3 仍可使用密码登录。通过排查发现，/etc/ssh/sshd_config.d/50-cloud-init.conf 中仍存在 PasswordAuthentication yes，导致最终配置未按预期生效。

随后将 50-cloud-init.conf 中的 PasswordAuthentication 修改为 no，并通过 sshd -t 检查配置语法、重启 SSH 服务，再次使用 sshd -T 验证，最终显示 passwordauthentication no、pubkeyauthentication yes。配置生效后，VM3 攻击端尝试使用 testuser / 123456 进行密码登录失败，说明 SSH 服务已不再接受密码认证。同时，VM1 管理端仍然可以使用私钥正常登录 VM2，VM1 管理平台也可以切换为私钥认证继续连接 VM2、查看日志并执行安全检查。

实验表明，禁用密码登录后，攻击者无法再通过密码字典猜测获得 SSH 登录权限；合法管理端仍可通过公钥认证方式完成远程管理。该防御措施能够有效缓解阶段 5 中验证出的 SSH 弱口令暴力破解风险。
