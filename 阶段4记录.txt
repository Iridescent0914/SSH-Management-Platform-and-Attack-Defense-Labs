阶段 4：实现平台核心功能并联调记录

一、阶段目标

本阶段目标是在阶段 3 已完成 Flask 基础框架的基础上，进一步实现 SSH 管理原型平台的核心功能，使平台不再只是占位页面，而是能够通过 SSH 连接 VM2 目标机并完成基础管理、日志查看和安全配置检查。

阶段 4 主要完成以下功能：

1. SSH 连接测试
   - VM1 平台通过 Paramiko 连接 VM2
   - 执行 whoami、hostname 验证连接是否成功

2. 白名单命令执行
   - 平台只允许执行预设命令
   - 不开放任意命令输入
   - 支持 whoami、hostname、uptime、systemctl status ssh、tail auth.log 等检测命令

3. auth.log 日志查看与统计
   - 平台通过 SSH 读取 VM2 的 /var/log/auth.log
   - 识别 Failed password、Accepted password、Accepted publickey、invalid user 等关键日志
   - 统计来源 IP、失败次数、尝试用户名和最近失败时间

4. sshd -T 安全配置检查
   - 平台通过 SSH 在 VM2 上执行 sshd -T
   - 解析 OpenSSH 最终生效配置
   - 展示 permitrootlogin、passwordauthentication、pubkeyauthentication、permitemptypasswords、maxauthtries、loglevel 等关键配置

5. 平台安全边界控制
   - 平台不保存密码
   - 平台不开放任意命令执行
   - VM2 仅为 testuser 配置受限 sudo 权限
   - 只允许执行指定检测命令

二、实验环境

本阶段继续使用前面阶段已搭建好的三台虚拟机。

三、阶段 4 实施思路

阶段 3 的 app.py 和 HTML 页面只是基础框架与占位页面，并没有真正连接 VM2，也没有执行真实 SSH 命令。因此阶段 4 需要对平台代码进行升级。

本阶段不是推倒重来，而是在原有项目结构基础上进行功能增强：

1. 备份阶段 3 文件
2. 升级 app.py 后端逻辑
3. 增加或替换功能页面模板
4. 补充页面样式
5. 启动 Flask 平台
6. 逐项验证平台功能

阶段 4 中使用 Paramiko 实现 SSH 连接，平台通过表单接收目标 IP、端口、用户名和认证凭据，并在后端建立 SSH 会话。连接成功后，平台只执行预先定义好的白名单命令。

四、VM2 配置受限 sudo 权限

1. 配置目的

在 VM2 上，普通用户 testuser 可以执行 whoami、hostname、uptime 等普通命令，但读取 /var/log/auth.log、查看 systemctl status ssh、执行 sshd -T 等操作通常需要更高权限。

为了避免给 testuser 开放完整 sudo 权限，本阶段采用受限 sudo 方式，只允许 testuser 免密执行指定检测命令。

这样既能满足平台功能需求，又能控制实验平台自身风险。

2. 在 VM2 上确认命令路径

在 VM2 上执行：

command -v tail
command -v systemctl
command -v sshd

正常结果通常为：

/usr/bin/tail
/usr/bin/systemctl
/usr/sbin/sshd

这些路径后续会写入 sudoers 配置中。

3. 创建 sudoers 配置文件

在 VM2 上执行：

sudo visudo -f /etc/sudoers.d/ssh_platform_stage4

写入以下内容：

testuser ALL=(root) NOPASSWD: /usr/bin/tail -n 100 /var/log/auth.log, /usr/bin/tail -n 200 /var/log/auth.log, /usr/bin/systemctl status ssh --no-pager, /usr/sbin/sshd -T

保存退出后，设置权限：

sudo chmod 440 /etc/sudoers.d/ssh_platform_stage4

检查 sudoers 配置语法：

sudo visudo -c

预期结果中应看到：

/etc/sudoers: parsed OK
/etc/sudoers.d/ssh_platform_stage4: parsed OK

4. 验证 testuser 的受限 sudo

在 VM2 上切换到 testuser：

su - testuser

输入密码：

123456

执行以下验证命令：

sudo -n /usr/bin/tail -n 100 /var/log/auth.log
sudo -n /usr/bin/tail -n 200 /var/log/auth.log
sudo -n /usr/bin/systemctl status ssh --no-pager
sudo -n /usr/sbin/sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication|permitemptypasswords|maxauthtries|loglevel)'

如果能够正常输出，说明平台后续通过 SSH 登录 testuser 后，也可以执行这些受限检测命令。

验证完成后退出：

exit

六、VM1 升级 app.py 后端逻辑

1. app.py 升级目的

阶段 3 的 app.py 只实现了页面路由和占位结果，不真正连接 VM2。阶段 4 对 app.py 进行升级，使其具备以下能力：

1. 使用 Paramiko 创建 SSH 连接
2. 支持密码认证和后续私钥认证
3. 执行远程命令
4. 限制远程命令只能来自白名单
5. 读取 VM2 的 auth.log
6. 解析 SSH 登录日志
7. 执行 sshd -T
8. 解析 SSH 安全配置
9. 将结果渲染到 Web 页面

2. app.py 中的主要功能模块

升级后的 app.py 包含以下核心部分：

1. DEFAULT_TARGET
   - 保存默认目标主机信息
   - 默认目标为 192.168.45.102:22
   - 默认用户为 testuser

2. WHITELIST_COMMANDS
   - 定义允许执行的白名单命令
   - 包括 whoami、hostname、uptime、systemctl status ssh、tail auth.log
   - 平台不允许用户输入任意命令

3. SECURITY_ITEMS
   - 定义 sshd -T 安全检查关注项
   - 包括 permitrootlogin、passwordauthentication、pubkeyauthentication、permitemptypasswords、maxauthtries、loglevel

4. create_ssh_client()
   - 使用 Paramiko 创建 SSH 连接
   - 支持 password 认证
   - 预留 key 私钥认证方式
   - 设置连接超时时间

5. run_remote_command()
   - 通过 SSH 执行远程命令
   - 返回 stdout、stderr 和退出码

6. parse_auth_log()
   - 解析 auth.log
   - 统计 Failed password
   - 提取 Accepted password 和 Accepted publickey
   - 提取关键原始日志

7. parse_sshd_T()
   - 解析 sshd -T 输出
   - 生成安全检查表格数据

8. Flask 路由
   - /
   - /connect
   - /commands
   - /commands/run
   - /logs
   - /security

3. /commands

/commands 是白名单命令执行页面。

页面提供下拉框选择命令，不提供任意命令输入框。

白名单命令包括：

1. whoami
2. hostname
3. uptime
4. systemctl status ssh --no-pager
5. tail -n 100 /var/log/auth.log

4. /commands/run

/commands/run 接收命令执行表单。

后端流程：

1. 检查 command_key 是否在 WHITELIST_COMMANDS 中
2. 如果不在白名单中，拒绝执行
3. 如果在白名单中，连接 VM2
4. 执行对应命令
5. 显示标准输出、错误输出和执行状态

该设计体现了平台安全边界：

平台只允许执行预设检测命令，不允许任意命令执行。

5. /logs

/logs 用于读取和分析 VM2 的 auth.log。

平台执行命令：

然后解析以下关键字：

Failed password
Accepted password
Accepted publickey
invalid user
Ban
banned

页面展示：

1. Failed password 统计表

   - 最近失败时间
   - 是否疑似暴力破解

2. 成功登录记录
   - 时间
   - 认证方式
   - 用户
   - 来源 IP

3. 关键原始日志
   - 展示最近的关键 SSH 认证日志

6. /security

/security 用于执行 sshd -T 安全检查。

平台执行命令：

然后解析以下配置项：

permitrootlogin
passwordauthentication
pubkeyauthentication
permitemptypasswords
maxauthtries
loglevel

页面展示：

1. 检查项
2. 当前值
3. 建议值
4. 风险说明

预期当前阶段的检查结果为：

passwordauthentication：yes
pubkeyauthentication：yes
permitemptypasswords：no

十三、常见问题与处理

1. 连接失败：Authentication failed

原因：

1. 密码输入错误
2. 用户名错误
3. 认证方式选错
4. VM2 上 testuser 密码不是 123456

处理：

在 VM1 终端手动测试：

ssh testuser@192.168.45.102

确认可以登录后，再回到平台测试。

2. 连接失败：timed out 或 Unable to connect

原因：

1. VM2 SSH 服务未启动
2. VM2 22 端口未监听
3. VM1 到 VM2 网络不通
4. IP 地址填写错误

处理：

在 VM2 上执行：

sudo systemctl status ssh --no-pager
sudo ss -tlnp | grep ':22'

在 VM1 上执行：

ping -c 4 192.168.45.102

3. auth.log 或 sshd -T 报 sudo 错误

现象：

sudo: a password is required
sudo: sorry, a password is required to run sudo

原因：

VM2 的 /etc/sudoers.d/ssh_platform_stage4 配置有问题，或者命令路径和 sudoers 中写的不一致。

处理：

在 VM2 上检查：

sudo cat /etc/sudoers.d/ssh_platform_stage4
sudo visudo -c

切换 testuser 验证：

su - testuser
sudo -n /usr/bin/tail -n 200 /var/log/auth.log
sudo -n /usr/sbin/sshd -T
exit

4. 页面提示命令不在白名单中

这是平台安全机制，不是错误。

说明：

平台后端拒绝执行不在 WHITELIST_COMMANDS 中的命令，避免 Web 平台变成任意命令执行工具。

5. logs 页面暂时没有 Failed password

这不是错误。

原因：

阶段 4 只是平台功能联调，还没有正式进行 VM3 弱口令攻击。阶段 5 攻击实验开始后，auth.log 中会出现大量 Failed password 记录，平台统计功能会更明显。

十六、阶段 4 结论

阶段 4 已完成。

当前 VM1 上的 Flask SSH 管理原型平台已经从阶段 3 的占位框架升级为具备核心功能的实验平台。平台能够通过 Paramiko 连接 VM2，执行受控的白名单检测命令，读取并分析 SSH 认证日志，并通过 sshd -T 获取 OpenSSH 最终生效配置。

通过本阶段实现，平台已经具备了后续攻击实验与防御验证所需的基础能力：

1. 后续弱口令攻击发生后，平台可以查看 VM2 的 auth.log。
2. 平台可以统计 Failed password 来源 IP 和失败次数。
3. 平台可以识别 Accepted password 成功登录记录。
4. 平台可以查看 passwordauthentication yes 的防御前状态。
5. 后续禁用密码登录后，平台可以再次通过 sshd -T 检查 passwordauthentication no。
6. 后续私钥登录实验中，平台可以识别 Accepted publickey 记录。

因此，阶段 4 的平台核心功能实现与联调工作已经完成，可以进入阶段 5：弱口令暴力破解攻击实验。
